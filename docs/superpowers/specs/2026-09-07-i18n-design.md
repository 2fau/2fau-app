# Internationalization (i18n) across app, extension, and site

**Status:** design (approved)
**Date:** 2026-09-07
**Branch/PR:** `feat/i18n` → `main` (single PR)

## Goal

Make the desktop app, browser extension, and marketing site fully translatable
from **one shared set of locale JSON files**, add language selection, wrap every
user-facing string in a `t()` call, and ship translations for the top ~12
Chrome-Web-Store languages.

## Decisions (locked)

- **English-as-key (gettext/Lingui style):** the source English string *is* the
  key — `t('Auto-Lock')`, `t("Passwords don't match.")`,
  `t('{count} minutes', { count })`. No invented dot-path ids. English renders
  even when a locale file is missing the key (identity fallback), so the UI is
  never blank. Identical English needing different translations is disambiguated
  with an optional context: `t('Download', { _ctx: 'nav' })`.
- **Shared model:** one package, `@twofau/i18n`, with per-locale JSON split into
  namespaces by surface (for bundling) — `ui` (app + extension + shared UI),
  `site` (marketing), `store` (extension manifest name/description/commands).
  Files map an English source string → its translation. App + extension load
  `ui`; the site loads `site`; the extension `_locales` are generated from
  `store`. A string reused across surfaces simply appears in both catalogs
  (English key, so no coordination needed).
- **Languages (12):** `en` (source), `zh-CN`, `es`, `pt-BR`, `ja`, `de`, `fr`,
  `ru`, `ko`, `it`, `tr`, `pl`.
- **Translations:** English lives in the code (the keys). An extracted `en`
  catalog per namespace lists the source strings for tooling; the other 11
  locales map each English string → translation, each file marked
  `"_meta": { "review": "machine" }` for later human review. English is the
  always-present fallback (identity when a key is absent).
- **Site selector:** Astro built-in i18n **routing** (`/` = en, `/es/`, `/fr/`,
  …) with per-locale `<title>`/description/OG and `hreflang`.
- **Runtime:** a **custom tiny runtime** (no react-i18next) — fits the project's
  minimal-deps ethos and keeps the MV3 bundle small.
- Ships via Knope: atomic Conventional Commits (`feat(i18n): …`) on `feat/i18n`;
  merging the PR to `main` lets Knope roll it into the next Release PR.

## Architecture

### `packages/i18n` (`@twofau/i18n`)

```
packages/i18n/
  locales/
    en/{ui,site,store}.json      # extracted source catalog (English -> English)
    es/{ui,site,store}.json      # English -> translation
    … (12 locales)
  src/
    index.ts          # core: createTranslator, interpolation, plural(), context
    react.tsx         # I18nProvider + useT() (React layer)
    locales.ts        # SUPPORTED_LOCALES, DEFAULT_LOCALE, resolveLocale()
    load.ts           # loadMessages(locale, namespace) -> dynamic import
  package.json        # exports ".", "./react", "./locales/*"; peer react optional
```

- **Core `t(source, vars?)`**: look up the English `source` string in the active
  locale's catalog; on miss (or no vars-only), use `source` itself (identity
  fallback — English always works). Interpolation replaces `{name}` tokens from
  `vars`. Optional `vars._ctx` disambiguates identical English with different
  translations; the stored key is `` `${_ctx}${source}` `` (gettext msgctxt
  convention), looked up before the bare source.
- **Plurals `plural(count, forms, vars?)`**: `forms` is `{ one, other, … }` of
  English strings; the catalog key is the `other` form, whose translated value is
  an object of CLDR categories. The category is chosen via
  `Intl.PluralRules(locale)`; falls back to the matching English form. `{count}`
  is interpolated.
- **`resolveLocale(tag)`**: maps a BCP-47 tag (e.g. `pt-BR`, `pt`, `en-US`) to a
  supported locale, else `DEFAULT_LOCALE` (`en`).
- **`loadMessages(locale, namespace)`**: `await import()` of that locale +
  namespace JSON. English is the identity fallback, so a target need not bundle
  `en` at all; only the active non-English locale is pulled. No target bundles
  all 12.
- **React layer**: `<I18nProvider locale messages>` holds the active locale +
  loaded catalog; `useT()` returns the bound `t` (and `plural`). A host loads the
  active locale's messages (async) and renders the provider; English shows
  immediately via identity fallback while a non-English catalog loads.

### App + extension

- `@twofau/ui` components call `const t = useT()` and replace every literal
  (text nodes, `placeholder`, `aria-label`, `title`) with `t('English text')`
  (or `plural(count, { one, other })` for counts).
- Each host wraps its tree in `<I18nProvider>`: the desktop app root, the
  extension popup root, the extension options root.
- **Locale is a setting.** Extend the `SettingsBackend` port:
  ```ts
  locale: { get: () => Promise<string>; set: (locale: string) => Promise<void> };
  ```
  Desktop: localStorage (like auto-lock). Extension: `chrome.storage.local`
  settings. Default when unset: `resolveLocale(navigator.language)`.
- **Language selector**: a new `SettingsView` row (drill-in list of
  `SUPPORTED_LOCALES` with native names), writing the setting and switching the
  provider locale live.
- The extension bootstrap and app `main.tsx` read the locale setting, call
  `loadMessages`, and mount the provider.

### Extension store localization

Web extensions localize the manifest via a fixed mechanism (Chrome & Firefox
both support it): a `default_locale` in the manifest, `_locales/<locale>/
messages.json` catalogs, and `__MSG_key__` placeholders that the browser
substitutes at load using `messages.json` (`{ key: { message, description? } }`).
`chrome.i18n.getMessage()` reads the same catalogs at runtime. Notably these
manifest catalogs use **short stable ids** (not the English-as-key convention the
app UI uses), because `__MSG_*__` placeholders must be identifiers.

- `manifest.json`: add `"default_locale": "en"`; `name`, `description`, and each
  command `description` become `__MSG_extName__` / `__MSG_extDescription__` / etc.
- **Generator** `scripts/gen-locales.mjs`: reads the `@twofau/i18n` `store`
  namespace per locale and writes `apps/twofau-extension/_locales/<locale>/
  messages.json` in the Chrome format. The `store` catalog is keyed by those
  short ids (`extName`, `extDescription`, `cmdAutofill`, …) mapping to the
  localized text. Wired into the extension's `build`/`package`/`dev` scripts;
  `_locales/` is gitignored (generated).

### Site (routed)

- `astro.config.mjs`: add
  ```js
  i18n: { defaultLocale: 'en', locales: ['en','zh-CN','es','pt-BR','ja','de','fr','ru','ko','it','tr','pl'],
          routing: { prefixDefaultLocale: false } }
  ```
  so `/` stays English and other locales are prefixed.
- **Server `t`**: `getT(locale)` (site helper) binds the `site` catalog for a locale;
  every `.astro` component reads `Astro.currentLocale` and calls
  `const t = getT(Astro.currentLocale)`. No prop-drilling.
- **Layout SEO per locale**: localized `title`/`description`, `og:locale`,
  `<link rel="alternate" hreflang>` for each locale + `x-default`, and canonical
  per localized URL.
- **Language selector**: a nav component listing locales, each linking to the
  current path under that locale (uses Astro's `getRelativeLocaleUrl`).
- **React islands** (`HeroCta`, `NavInstallButton`): receive a server-resolved
  **dict of just the strings they use** + the `locale`, as props, so they don't
  bundle all locales. (Their store links already come from `config/links.ts`.)

### Tooling

- `scripts/extract-i18n.mjs`: scans the codebase for `t(...)` / `plural(...)` /
  `getT` calls (and the `store` ids) to build the **`en` source catalog** per
  namespace — the list of English strings actually used. Writes/refreshes
  `locales/en/*.json` (identity) and adds any new source strings to every locale
  file with an empty/marked value.
- `scripts/check-i18n.mjs`: verifies every locale has exactly the `en` source set
  (reports missing/untranslated/orphaned keys) — run in CI (`ci.yml`) and locally.
- Keys are plain strings (the English source), so there is no generated key
  enum; TS callers pass string literals. `extract-i18n` is the source of truth
  for which strings exist.

## Testing / verification

- Core: unit tests for lookup, `en` fallback, interpolation, plural selection,
  `resolveLocale`.
- UI: existing Vitest suites keep passing; tests that assert English text run
  under the default `en` provider (add an `I18nProvider` test wrapper).
- `check-i18n` passes for all 12 locales (no missing/extra keys).
- `pnpm -r build` green; `astro build` emits per-locale routes; extension
  `_locales` generated and `web-ext lint` clean; app + extension typecheck.
- Manual: switch language in settings (app/extension) and via the site selector.

## Task breakdown (each an atomic `feat(i18n)` commit)

1. **Core package** `@twofau/i18n`: runtime (`t`, `plural`, context, interpolation,
   identity fallback), React layer, locales list, loader, `extract-i18n` +
   `check-i18n` scripts, unit tests.
2. **App/extension wiring**: `SettingsBackend.locale` port + impls, `I18nProvider`
   at the three roots, wrap all `@twofau/ui` strings with `t('English')`, run
   extraction to populate `en/ui.json`, add the settings language selector.
3. **Extension `_locales`**: manifest `default_locale` + `__MSG__`, `gen-locales`
   script, build wiring, gitignore.
4. **Site i18n**: Astro i18n routing, `getT`, extract `site.*`, wrap every site
   component, localize Layout SEO + hreflang, nav language selector, island dicts.
5. **Translations**: machine-translate the 11 non-en locales for all namespaces,
   marked for review; `check-i18n` script + CI wiring.
6. **Verify**: full build/test/lint across all packages; fix fallout.

## Out of scope

- Human/professional translation review (translations ship machine-marked).
- RTL languages (Arabic/Hebrew) — deferred (layout work); the 12 chosen are LTR.
- Localizing generated/legal docs (PRIVACY.md, store-listing copy) — English only
  for now, except the extension store `name`/`description` via `_locales`.
- Number/date/currency formatting beyond plurals (not needed by current UI).
